# Code rewind

The existing return-here action offers conversation only, code only, or both. The selected user turn is inclusive: code restore returns files to the state before its first tracked edit and reverses later tracked edits in that session. Conversation restore removes the selected user message and everything after it, returning its input to the composer. Code-only restore preserves the transcript, composer and queued messages. Edit-and-resend and fork retain their existing filesystem behavior.

Checkpoints capture original bytes immediately before authorized local `write_file`, `edit_file`, `multi_edit`, `apply_patch`, `move_file`, and `delete_file` effects. They are grouped by the initiating user message and survive restart. Creation records prior absence, so restoring it deletes the new file. Deletion preserves bytes and mode. Moves track both source and destination, including an overwritten destination. Multi-file patches record each effect before that effect runs; a failed patch can retain earlier applied effects.

Shell commands, including bash side effects, are not checkpointed. File transfers and remote workload edits make code restore unavailable for any selected range crossing their turn. Each executing child, including a resumed child, blocks code restore for its origin session until its lifetime ends. Background or detached children remain counted until completion, failure or cancellation has finished. Every parent turn overlapping a live child stays unavailable, including later turns after dispatch. New parent turns can create usable checkpoints once all children have ended. Child turns do not create separate code checkpoints or consume the profile turn cap. Missing or pruned checkpoints refuse explicitly; a vanished in-flight record invalidates its session's surviving restore ranges. Conversation-only restore remains available. Rewind does not replace version control.

Code restore retains hash guards for its restored baseline. Repeating that restore checks for external changes again. Later code checkpoints whose edits were undone become unavailable; they cannot silently succeed as forward restores. Earlier checkpoints and new turns can still rewind through the restored baseline.

Before restore, all affected files must pass the current write-directory and sensitive-path checks and match the last native edit's SHA-256 hash, or be absent after a deletion. Gaps between consecutive edits also refuse, protecting external changes made between agent edits. Refusals list conflicting paths and leave files and conversation untouched. An uncapturable original, including a symlink, hard link or oversized file, makes the turn unavailable without blocking an authorized edit. Restore refuses links, special files, changed ancestor resolution and oversized files. It stages replacement bytes and rechecks policy and hashes before applying changes.

Concurrent external writers cannot be locked by the host. An I/O failure during replacement can leave a partial restore and returns failure without truncating the conversation. The original checkpoint remains on failure, but already restored files can then conflict with its expected after-hashes. Inspect the affected files and recover using version control before retrying.

[CODE_CHECKPOINT_POLICY](../../src/shared/code-rewind.ts) owns the limits: 8 MiB for either image of a file, 100 turns per session, 500 turns and 64 MiB retained serialized storage across the profile. Oldest whole session prefixes are pruned on admission. In-flight restore ranges are pinned; if their originals cannot fit, the affected turn becomes unavailable and the authorized edit continues. Pinned metadata may temporarily exceed the turn caps until those turns settle.

The private `code-checkpoints` feature namespace stores a versioned `turns.json` metadata index and immutable `image-<uuid>.json` before-images. An edit writes only its new images and the small index, with atomic private-file writes and no-follow, identity, ownership and link-count checks on reads. Staging briefly needs space alongside retained files. Legacy inline ledgers migrate on first access: images are written before the index is replaced. A failure before index commit leaves the legacy ledger untouched, removes partial images and retries on a later load. If a writer reports a durability error after committing the index rename, its referenced images are preserved. Lock and permission read failures get bounded retries on Windows; persistent I/O failures make the current turn unavailable while its authorized work continues. The ledger is preserved. Deferred unavailable markers retain the newest 100 turn IDs per namespace and session. A dropped older ID needs no marker: every restore range that reaches it also contains the newer retained placeholders, so it is refused. Recovery persists the retained markers under the normal turn caps. Successful persistence or session deletion clears the deferred state.

Only parse, schema and storage-validation failures quarantine a ledger to `turns.json.corrupt-<timestamp>-<uuid>.bak`; its old restore points become unavailable while new turns continue. Before moving the ledger, a private `<backup>.images.json` manifest records the image filenames then on disk, including orphans, without parsing the damaged index. The manifest uses the same atomic 0600 writes and no-follow, identity, ownership and link-count read checks as other storage. A sidecar keeps image paths stable and reuses the existing private-file checks. Later unreferenced images are collected normally.

Quarantined backups, manifests and their unique preserved images share a separate 64 MiB profile budget (`maxQuarantineBytes`). Oldest whole evidence sets are discarded when this budget is exceeded. Shared images survive while another retained set or the active index references them. Together with the active 64 MiB budget, the namespace retains at most 128 MiB after a successful sweep, excluding temporary staging and pinned metadata. Missing, unreadable or invalid manifests discard that backup's preservation claim and backup; unreferenced images are then collected. This favors bounded storage over unverifiable evidence, including backups from older versions without manifests. Orphan manifests are removed. Removing a backup releases its manifest and preserved images at the next sweep. Session deletion removes its index entries, all quarantined backups whose ownership cannot be recovered, their manifests and then unreferenced images; other sessions' active images remain. Failed cleanup is warned and retried on a later save; storage that refuses deletion cannot enforce the byte bound until access recovers. Downgrades and quarantine emit warnings with their reasons. File tools retain their existing authorization, fresh-read checks and broker routing.

## Latest-turn change review

Main-chat conversations can review only their latest user turn after its assistant and tool work has settled. The host selects that turn from its history; an older turn is never substituted when the latest has no tracked changes. Review is unavailable during streaming, session transitions or overlapping child work, and for missing, consumed or incomplete checkpoints. A captured turn without tracked changes returns an empty review.

The host derives independent text hunks from the turn's original checkpoint bytes and final file state, checking continuity between tracked edits. Tool-result snippets are not the source of the diff. Common unchanged lines separate hunks; excessive diff complexity falls back to one whole-file hunk. Binary, invalid UTF-8 and oversized content cannot be reviewed. This covers bounded local file-tool effects only; shell, external-writer, file-transfer and remote-workload effects remain outside checkpoint capture.

Accept records a final decision without changing the file. Reject reverses one pending hunk while preserving accepted and other pending hunks. Every review load and decision checks each tracked file's complete contents against its expected SHA-256 hash, accounting for earlier rejected hunks. Rejection checks again before its file effect. If this pre-effect check finds a changed file, rejection refuses with a conflict; nothing is reverted and there is no force option. Creation and deletion use whole-file hunks: reversing creation deletes the file, and reversing deletion recreates it. Recorded decisions are final, and each decision changes the review version so stale requests refuse.

Hunks, decisions and rejection recovery metadata live in the existing checkpoint ledger and survive restart within its retention limits. The host serializes checkpoint operations and records a pending rejection before executing it. After interruption, review recovery compares the current file with the recorded before/after hashes: an applied effect finalizes the decision, an unapplied effect clears the pending attempt, and any other state refuses review with a conflict. Recovery never rewrites the file automatically. A failed ledger save returns failure rather than claiming a persisted decision; a successful code rewind invalidates the obsolete review.

Reject uses the same tool permission, approval, hooks, audit and file transport as ordinary authorized file edits. Policy checks also protect snapshot reads. The renderer submits only session, turn, version and hunk identifiers plus its decision; the host supplies the path and replacement bytes. Local checkpoints refuse a broker route instead of authorizing a remote write. The file effect rechecks policy and the expected full-file hash after approval and hooks. Concurrent external writers cannot be excluded atomically, and an I/O or persistence failure can leave an applied file effect awaiting recovery; review does not promise a transaction across the filesystem and ledger.

## Comparison with Claude Code

Source: [Claude Code checkpointing](https://code.claude.com/docs/en/checkpointing), accessed 2026-10-22. Claims not listed as matching are Ave's own design.

Matches Claude Code:

- Conversation-only, code-only and both restores at a prompt that starts a turn; conversation restore returns that prompt to the input.
- File-editing tool changes are tracked; Bash side effects and external edits are not. Checkpoints survive resuming a conversation.
- 100 checkpoints per conversation.
- Rewind does not replace version control.

Intended differences:

- Claude Code skips symlinked and hard-linked paths and restores the rest with a warning. Ave refuses the whole restore and lists conflicting paths, including externally changed files, rather than skipping part of the selected range.
- Claude Code removes snapshots in a retention sweep, by default about 30 days after the session last saved one, and keeps each file's first snapshot when discarding older checkpoints. Ave has no time-based sweep. It prunes oldest whole turns to the 100-turn, 500-turn and 64 MiB caps, so surviving restore ranges stay complete.

Additional behavior includes the 8 MiB per-image, 500-turn and 64 MiB profile limits; hash guards and consumed later checkpoints; unavailability across file transfers, remote edits and subagent dispatch; and partial-restore disclosure on I/O failure. Summarize actions and mid-turn queued messages are out of scope here.
