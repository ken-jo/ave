# Windows container prototype measurements

Run these before implementing the [extension migration](../../docs/design/windows-extensions-mxc.md#prototype-gate). Each of the five entry scripts prints **one JSON line** to stdout. They measure prerequisites, not a passing production sandbox. The toolkit performs no explicit persistent package/service/firewall/ACL installation. Its own file writes, compiled helper paths, HOME/LOCALAPPDATA/TEMP environment values and retained evidence are directed to a fresh OS temp directory. OS/SDK-managed effects are separate: host Windows PowerShell 5.1 compilation may populate StartupProfileData or ModuleAnalysisCache under the real known-folder profile despite environment overrides, and PSEC applies privileged per-container WFP and WinHTTP proxy state. The toolkit does not promise that these managed writes/state changes stay under temp or attempt profile-cache cleanup. The local HTTP proxy refuses every request and makes no upstream connections. Kernel fixtures are ephemeral, uniquely named, and never open live Ave pipes or change the registry.

## Prerequisites and invocation

Use a **standard-user interactive desktop session** on the Windows peer, not an SSH/service session. The supervisor records `sessionId` and refuses session 0. A supported OS version alone is insufficient: each exact request must probe as `base-container` without DACL augmentation. The toolkit never performs host preparation. If the host needs preparation, report that separately; do not grant it implicitly through these probes.

Supply an operator-trusted, separately staged `@microsoft/mxc-sdk` **1.0.1** directory including its installed runtime dependencies, and a trusted Node executable satisfying the SDK native-stream gate (`>=24.21 <25` or `>=26.8`). The supervisor checks the SDK version and the selected architecture's `mxc_ffi.dll` hash against [sdk-pins.json](sdk-pins.json), derived from the published [1.0.1 archive](https://registry.npmjs.org/@microsoft/mxc-sdk/-/mxc-sdk-1.0.1.tgz). Archive SHA-512 base64: `2cP925G5+lQyKzjBVha8uNtVd7XESgDBtgi1yCYYSo9M3xiFyZWtCO4SWPGTk509rdI6nqjyGcZxvEP3t6l8Hg==`.

The scripts do not download or install the SDK. Use a verified extracted/staged SDK with dependencies already present; missing native dependencies produce an error, not an automatic build/download. `koffi` is an operator-trusted bootstrap prerequisite; prototype DLL-search restrictions take effect after its addon loads. This does **not** validate the production requirement to restrict search before any native addon loads. Runtime, SDK and dependency directories are read-only inputs. Run only trusted toolkit files.

The driver is standalone Node; `--runtime` is the child being measured. Environment is stripped and `ELECTRON_RUN_AS_NODE=1` is set for the child, so an electron.exe path tests its Node mode. Repeat loopback/lifetime/object probes with standalone Node when comparing runtimes. Architecture follows the driver; use an arm64 driver and matching staged SDK/runtime for arm64 evidence. Native PowerShell fixture compilation uses the source copied into that run's temp directory and explicitly references System.dll (including Regex) and System.Core.dll (Pipes/MemoryMappedFiles); the other helper types use implicitly referenced mscorlib. PowerShell's own cache writes are OS/runtime-managed effects, not confined by those output paths. Do not point `--runtime` at an installer or an untrusted executable.

Record OS build (`[Environment]::OSVersion.Version`), exact driver/runtime paths and hashes (`Get-FileHash -Algorithm SHA256`), session, architecture and each JSON line in the review evidence. `observation.node` is the driver's bundled version; the `runtime-started` child record identifies the child runtime. The request uses a fresh cwd/HOME/temp, explicit runtime/SystemRoot reads and a temp-only write root. These intentionally generous diagnostic read roots do not certify production filesystem policy.

## Ancestor-query rerun

The Windows peer's f19e1dc87 run reached Node's main-module realpath with UI enabled but failed at `lstat D:\` before executing the script. The request now retains leaf file read/write grants and adds only their uncovered ancestors under SDK `containment.config.filesystem.enumeratePaths`. This is query/list access, **not** file-content read access or invisible traversal; it can expose names/metadata. Whether fs_enumerate cascades into subdirectories is unverified. With default tmpdir under the real user profile, granting its ancestors may expose sibling names/metadata under that profile and its parents even though HOME is redirected. Prefer a dedicated staging/temp tree and test descendant name reach separately. It requires native PSEC 1.1 enumeration support. The exact list appears in `observation.filesystemPolicy` when all attempted launches use one policy, and in `observation.filesystemPolicies` for every distinct attempted policy (the singular field is null before a launch or for a mixed set). Ordinary rows and the lifetime/kernel peer rows carry their actual `filesystemPolicy`; kernel/shell native commands report `entryVariant:"native-command"`, while runtime file entries report `"script-file"`. Extra Git runtime roots can make shell policies differ. These fields describe requested policy, not effective enumeration scope; `driveRootRead:false` records that no root file-read grant was requested. Runtime/data staging directly at a drive root is refused. Unsupported enumeration produces an inconclusive/error result before spawn; there is no broad drive-root read fallback. See [the design finding](../../docs/design/windows-extensions-mxc.md#ancestor-query-access-for-entry-resolution) and [the pinned schema](https://github.com/microsoft/mxc/blob/fda29ac63bc306b7f97f3b86b4b63d44f7f40cf2/docs/schema.md#L382-L420).

The public SDK supports this narrow form, so no Node-side `--preserve-symlinks-main` or `-e`/stdin workaround is selected. The child and grandchild still execute the same file payload. The ca22a44ab peer rerun started the UI-enabled runtime successfully with the revised policy and identical before/after host DACL snapshots. Same-container loopback was denied (EACCES), disproving D1 option 1 under this proxy policy; child and grandchild were independently confirmed dead after dispose. See [the measured results](../../docs/design/windows-extensions-mxc.md#windows-peer-results-at-ca22a44ab). These are one-host observations, not packaged production acceptance.

UI-disabled exit `0x80000003` and Bash failures remain expected observations, not an invitation to broaden filesystem grants. Git Bash hooks stay on their independently admitted srt-win/shell-plan route.

`kernel-objects.cs` creates its own pipe/section/ALPC fixtures using the process's default DACL and reads only `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\CurrentBuildNumber`. ALPC status/timeout or failed host baseline must stay unknown. ALPC signatures follow the [native API declarations](https://github.com/winsiderss/systeminformer/blob/7356a5f48923eafc4696feafd1e5081ed78faeda/phnt/include/ntlpcapi.h); Windows compilation and behavior still require the peer run.

## Verdicts, lifetime and retained temp data

Abbreviated UI rows matching the ca22a44ab measured outcome (full metadata omitted here):

```json
{"probe":"node-ui","verdict":"measured","details":[{"uiDisabled":true,"exitHex":"0x80000003","stdout":""},{"uiDisabled":false,"exitCode":0,"stdout":"{\"marker\":\"runtime-started\"}\n"}]}
```

`verdict: "measured"` (exit 0) means observations completed, **not** that every UI/shell combination worked or that confinement passed. Inspect every row's exit code, marker and stderr. `inconclusive`, `unavailable` and `error` exit 2. Native crash, missing dependency, session 0 and timeout (including SDK WaitResult.timedOut) cannot become success. A session-0 prerequisite failure is unavailable; in a verified interactive session, UI-disabled `0xC0000142` remains D3 startup evidence, not an automatic unavailable-host classification. SDK/native stdout diagnostics are captured by the outer driver so its public stdout remains one JSON line. Spawn passes one SDK argument and asserts telemetry is absent; no consent or telemetry calls are made.

Budgets are read from [the shared timeout policy](../../src/shared/tool-timeout-policy.ts); an unrecognized policy shape fails closed. SDK child deadlines use that policy. The lifecycle fixture deliberately omits a child deadline to measure disposal, while the independent driver retains an outer deadline. On ordinary completion each process is waited/disposed; exact pinned process handles may terminate **only the fixture child/grandchild** during lifetime cleanup. On a supervisor crash or outer deadline, descendant cleanup is unverified: retain the JSON error, confirm the fixture processes are gone on the peer and do not mark the gate passed. This toolkit does not yet provide the production kill-on-close supervisor job.

Temp directories are created automatically, intentionally retained for review and named in the verdict. `driver.json` records the supervisor PID/path/start time; `events.jsonl` records known SDK fixture PIDs, their commands and child/grandchild readiness before disposal. A crash before a journal entry can leave incomplete identity evidence. Read the journal, then independently compare PID, creation time, executable and command line with `Get-CimInstance Win32_Process`. For a missing entry, query command lines containing the **exact random temp-directory token** to identify only this run’s fixtures; do not infer ownership from an executable name alone. Shell-start commands also contain that token. Supervisor identity is checked against `driver.json`, not a broad process-name search. If identity/death cannot be proven, retain the run as inconclusive and do not automatically terminate an ambiguous PID. After exact fixture identity and termination are confirmed, remove only that exact `ave-mxc-probes-*` directory after confirming its helper/fixture processes have exited. No wildcard process kill, profile cleanup, ACL reset or deletion outside that directory is part of the probes. No production settings, secrets or project files are needed.

An identity-route prototype is future work outside the decided D2 option 2 scope; these probes never create package identity or an administrator firewall rule. Native module-loading hardening, host/supervisor crash, production DLP/listener ownership and registry write-right testing remain release gates. An ordinary service-hosted CI job is not interactive evidence: use the dedicated desktop-session runner specified in the design.

## Packaged extension-process acceptance

Plugin streams use the existing protocol and owned process primitive. The internal [`prepareMxcChild` hook](../../src/plugins/isolation/out-of-process-plugin.ts) accepts an [admitted launch](../../src/plugins/isolation/mxc-plugin-child.ts). The adapter refuses a request whose command is not `windowsCommandLine(command, args)` or whose working directory is not the derived cwd, compared exactly; binding the write grants to the captured envelope belongs to the backend-policy owner. That owner must supply this hook; this stream change does not select a backend or publish a capability marker. Backend selection is unchanged, so default execution still uses the existing confined-child path, but that path now shares three stricter stream rules: a bounded outbound queue, a child stdout writer that acknowledges only after the underlying write, and refusal of host effects once the transport has closed. In the child, MCP tool results wait for protocol stdout to drain before the next one is framed. The effective child-to-host limit therefore sits in the child's MCP output, which may hold at most `OUTBOUND_QUEUE_BYTES_MAX` unwritten; a response past that is refused as an error reply for that call (`payload-too-large`) instead of being buffered without limit, while host-to-child requests and cancellations keep flowing. Portable process-pipe tests imply no native readiness. A cleanup failure retains the launch lease, envelope registration and generation payload, rejects `waitForExit` with `PluginChildTerminationUnverifiedError`, and quarantines the plugin lifecycle so replacement is refused. A bring-up failure is reported only once termination is known. While a child's termination is pending or quarantined, no replacement registers, and a replacement that registered earlier is refused by a synchronous recheck immediately before (and after) its spawn; a quarantined lifecycle never publishes a replacement and reports failure. The planner must pass the intent cwd through verbatim (no trailing separator, case change, forward slashes or realpath). No effect is replayed.

In a standard-user interactive Windows x64 session, run the verification build and driver commands below. The driver includes both plugin-stream rows; no account setup or ACL repair is part of this harness. Rebuild after changing stream or probe sources. Save `mxc-packaged-observations.jsonl` and inspect all eight rows, their hashes and the independently pinned process-death evidence described below. An unavailable host or failed row remains unverified. Plugin rows build their command with the production `windowsCommandLine` and pass the adapter's `assertLaunchMatchesIntent` before spawning; they still attach the owned process directly rather than through `spawnMxcPluginChild`, because the controller must pin the supervisor and container itself. [`plugin-stream-session.ts`](plugin-stream-session.ts) imports the production frame limit and centralized deadlines; each of eight 786,432-byte Unicode results records its actual byte count, SHA-256, subscription value and the bytes waiting in the paused reader (`pausedBacklogBytes`), with one `processGroupPollMs` reader pause per result. `handshake`, `subscription` and `slowReadCycles` are measured in the run: the construct reply's implemented tools, the registered watcher count and the delivered value, and the number of pauses that actually held output. The overflow row expects a controlled frame-overflow rejection followed by verified container termination. It records the exact limit and refusal, rather than treating a runtime crash as success.

The app used as driver must be the same locally built payload being measured. Its Node mode runs the standalone controller, which verifies the packaged SDK and runtime bytes before loading the verified observer addon. The diagnostic main uses that untouched original package for its independent pin inspector, including in the planted-DLL case; the public primitive and its supervisor still verify only the mutable copied package. This keeps the negative control on the real public spawn path. The observer has **no outer lifetime job**, so it cannot mask the main-death EOF test. The controller copies the app into one fresh `ave-mxc-packaged-*` OS-temp directory and refuses redirected source files before copying. Source validation, copying, retained-size walks and recursive cleanup temporarily set `process.noAsar = true`, treating `app.asar` as one ordinary file; `finally` restores the prior setting before archive entry loading. All measured processes execute from that copy. The planted DLL is added only to the copy's unpacked SDK bin directory. The real package/install and repository dependencies are read-only inputs.

The filesystem audit also covers the controller's exact executable/journal/DLL reads, observer module-path resolution, fixture journal writes, public spawn entry and supervisor bootstrap. Production integrity walks are confined to `app.asar.unpacked/node_modules`; runtime verification reads the exact `resources/mxc/<arch>/supervisor-runtime-pins.json` and enumerates only the executable's immediate directory. None recursively walks the resources archive. The supervisor and diagnostic main intentionally load their entry from `app.asar` with archive handling enabled. Archive handling is restored before either bundled entry loads.

Each row pins the main process through an owned nonce challenge. The diagnostic main pins its supervisor synchronously in the public spawn callback, holds the exact process object across even a fast startup rejection, and lets the controller duplicate that object before release. Container fixtures publish atomic PID/token journals and answer fresh file-based nonce challenges while held before stdio transfer. Every successfully admitted process object requires matching PID, creation time, executable-image evidence and terminal signaling; a PID's absence or a failed temp deletion is never death evidence. Survivor records name the exact pinned role, PID, creation time and image path before cleanup.

All modes, including cancellation, await an explicit controller `release` before closing supervisor or container pins. `case-complete` reports `controlsClosed`; a disconnected controller is a `HarnessHandleLifetimeError`, exit 2, rather than implicit release. On that failure the pins remain owned until the diagnostic process exits. After duplicating a process handle, the controller checks its PID before querying creation time or executable identity. A mismatch reports expected and actual PIDs and a possible handle-lifetime race; a failed PID query is reported separately. A matching PID still requires a successful creation-time query. Identity-query failures name the native call and error code. For the cancellation container only, a failed image query can use live pin-time image evidence when the duplicated handle is already signaled, its PID and creation time exactly match the pinned frame, and the resolved pin-time image matches the copied executable. The main marks `aliveAtPinTime:true` only if the object is unsignaled both before and after its identity query. Accepted records carry `identityEvidence:"exited-before-duplication: pid+createdAt+pin-time image"` and the image-query error code. A running handle, missing live image evidence, failed time query or any identity mismatch remains a hard failure; an image-query failure alone never establishes death. Changes to the bundled diagnostic main or observer require rebuilding the verification app even when all edits are under this toolkit.

The JSON `observations` array contains:

- `packaged-stdio-bytes-eof`: a held, identity-confirmed container sends exactly 4 MiB, the SHA-256 must match, and stdin EOF must produce the expected stderr marker and successful exit. This proves byte count, hash and EOF only. It does not claim measured end-to-end backpressure.
- `packaged-plugin-streams`: the existing child runtime constructs through native stdin/stdout, registers a HostApi config subscription, receives a change, and returns eight large Unicode results with matching hashes while the reader pauses once per result. Every pause must hold output (`slowReadCycles` 8). A forged owner/generation with an unissued invocation token must refuse before the host effect runs: the refusal message must name the unheld invocation (the shape check shares its code), and the forged `pluginId`/`generationId` must be reported as ignored fields against the real connection. Revocation must close admission, dispose the handle and release every watcher and the policy lease exactly once. The pauses exercise the child-to-host direction only, as transfer under a slow host reader; they do not measure kernel buffering, and the host-to-child outbound queue bound is covered only by the portable `child-stream-multiplex` unit test.
- `packaged-plugin-overflow-streams`: a separate held plugin child writes at most 64 MiB without a delimiter, bypassing the writer only for this negative control. The production frame decoder must reject at its existing limit and the container must die. Nonblocking fixture writes handle partial writes and EAGAIN.
- `dispose`, `main-death`, `supervisor-death`: nonce-confirmed container and grandchild objects must still be live immediately before the action and independently signaled afterward. `survivorsBeforeCleanup` records any still-live pinned objects before survivor termination. The observer separately records resolved supervisor module paths; authenticated diagnostics include their total count and any truncated selected-first diagnostic list.
- `fd3NonInheritance`, within each lifetime row: decode the supervisor owner pipe's object type, compare only descendant handles of that same type, require at least one successfully inspected matching-type handle per descendant, and require no matching owner object. Unrelated, non-duplicable handle types are not inspected. Empty/no-matching snapshots, failed matching-type duplication, unsupported comparisons and incomplete snapshots are inconclusive.
- `cancel-during-native-spawn`: cancellation starts at the authenticated `spawning` receipt after SDK invocation. The authenticated stop receipt must confirm that cancellation overlapped the pending native await. Immediately after native spawn resolves, the supervisor opens a non-inheritable query/synchronize handle to the container PID, before disposal. Its authenticated `native-created` receipt lets the diagnostic main duplicate that process object synchronously before acknowledging it. The main retains its duplicate until the outer controller has independently duplicated and checked the PID, creation time and executable. `containerObservationComplete:true` requires that exact object; successful cancellation additionally requires `WaitForSingleObject == 0` on the container, main and supervisor. No post-disposal fixture journal or live-child acknowledgement is needed. A missing duplicate, surviving process or cancellation timing miss cannot pass. The cancellation fixture never spawns descendants; the three lifetime rows independently test container and grandchild death. No lifetime job handle is duplicated.
- `planted-dll-before-load`: a real extra DLL in the copied unpacked SDK directory must produce `MxcIntegrityError` identifying `@microsoft/mxc-sdk/bin/x64/planted.dll`, before any native creating/readiness receipt. That authenticated pre-creation failure establishes `containerNotCreated:true`; main and supervisor termination are still checked through their pinned objects.

`verdict:"measured"`, exit 0, requires all eight rows and process cleanup checks to pass. Native failure, unsupported APIs, a cancellation timing miss, unpinned ownership or incomplete evidence returns `inconclusive`/`error`, exit 2. This implementation has **not been run on Windows**; portable tests establish only fixture IO, parsing, bounds and evidence classification. Record the actual JSON.
